## 1. 目标和实施原则

让首次进入商城的用户能理解商品价格、主动开团或加入他人团队、完成模拟支付、查看拼团和退款进度。普通用户只需要理解“买什么、付多少、下一步做什么”，不必理解A/B、占位、渠道尝试、消息确认或租约。

本轮重点是可用的商城体验，不以增加页面装饰或新技术栈代替流程优化。继续使用现有Vue3、TypeScript和Vite，优先整理共享组件、样式及页面状态；首轮不因换肤引入新的UI框架、注册中心或推荐服务。前后端仍分离，用户统一访问B，A通过既有契约参与交易。

业务约束保持：单SKU、数量1、模拟支付、已支付不主动退团、失败自动全额退款、成团仅待履约。不能添加没有后端能力的购物车、发货／收货、部分退款、真实支付按钮，也不能因页面减少点击而放宽确认报价、购买守卫和未知结果恢复。

主要验收目标：

- 登录后的普通开团常态流程压缩为“单独开团→确认下单并去支付→模拟支付成功”三次主要操作，不计登录输入、异步等待或价格变化重新确认。
- 用户能从商品详情发现并加入别人团队；每页都明确当前状态、主要操作及异常恢复入口。
- 普通页面默认不显示UUID、商品版本、FORMING、营销同步和原操作键；支持信息可折叠查看／复制，数据仍完整保留。
- 页面不再暴露HTML解析错误、堆栈或内部英文码；维护状态明确展示，真正开放的网关才通过开放就绪检查。
- 桌面和移动端都可操作，样式覆盖购买、订单、支付与退款，不只美化首页。

## 2. 现状问题与优先级

依据当前App、Products、PurchasePanel、Team、Payment、Orders、RefundProgress、auth服务和全局CSS核查；不是仅凭截图推测。

| 优先级 | 当前问题 | 用户受到的影响 | 优化方向 |
| --- | --- | --- | --- |
| P0 | 网关维护时返回HTML503，前端直接response.json | 点击开团出现Unexpected token，无法判断原因 | 统一错误处理、维护反馈与真实网关门禁 |
| P0 | 控制器主要检查镜像／schema／GET查询，未确认交易入口开放 | 检查通过但仍不能下单 | 区分存活、依赖可用、对外开放三层状态 |
| P0 | UX 继承的部署入口尚未单独验证重复启动／开放的前置拒绝 | 误用 UX 启动命令可能改变已开放入口 | 在 UX 独立环境区分前置拒绝与切换后失败；旧站稳定入口已有重复启动验收 |

| P1 | 模拟支付需先创建尝试，再选择结果，再手动查询 | 为完成一次演示需要理解渠道内部模型 | 用户选择结果后，前端安全编排既有操作 |
| P1 | 品牌链接导航到登录，标题固定“知集商城·账号” | 找不到自然首页，标签页不能反映当前页面 | 正经商城品牌回首页、页面标题与导航状态统一 |

| P1 | 普通购物和运营操作共用顶栏；账号页显示验证运营权限 | 干扰购物、混淆身份职责 | 用户布局与运营布局分离，权限仍由服务端判断 |
| P2 | 列表、移动布局、空／加载／异常状态缺少一致设计 | 浏览和异常恢复成本高 | 统一组件、响应式和辅助访问 |

P0先做并验收，再进入大面积视觉重构。上一轮恢复网关只解决运行配置，不等于上述代码问题已经修复。

## 3. 信息架构与品牌改名

### 3.1 页面组织

用户页面保持现有可分享路径：

| 页面 | 职责与主操作 |
| --- | --- |
| `/`、`/products` | 商城首页／商品列表，进入商品详情 |
| `/products/{goodsId}` | 展示商品、当前优惠、待拼团队，单独开团或选团 |
| `/teams/{teamId}` | 展示当前团队、可加入条件、本人订单，确认加入或分享 |
| `/orders`、`/orders/{orderId}` | 订单概览／详情，去支付、看拼团、取消未付单、看退款 |
| `/orders/{orderId}/payment` | 模拟收银台与结果反馈 |
| `/login`、`/register` | 身份验证；完成后返回安全的原商品／团队／订单路径 |
| 账号中心 | 已登录资料与退出，不再承担商城首页职责；具体新增路径在UX-01冻结 |
| `/admin/*` | 运营工作台，普通用户没有入口且服务端继续拒绝越权 |

抽取统一站内导航方法，替代App中手写映射与其他页面各自pushState／整页跳转混用。首轮可整理现有轻量路由，不强行新增依赖；必须覆盖返回／前进、刷新深链接、未知路径404及登录回跳。不得把未知路径默认伪装成登录页，也不得放宽现有returnTo站内白名单。

### 3.2 品牌变更清单

统一名称“正经商城”；左上品牌可简写“正经”，辅助英文不作为必需装饰，首轮以中文名称为主。

- App品牌、账号页、页脚；品牌链接改为商城首页。
- `frontend/index.html`默认title、各页面动态title，例如“商品名称｜正经商城”“我的订单｜正经商城”。
- 用户可见的ZHIJI／知集文案、页面说明、测试期望与新交付操作说明。
- 使用文字品牌或本地简洁SVG，不引入外链字体／图片依赖；图标有可访问名称。

改名只针对对外展示，不改 `zj-market` 工程名、Maven坐标、数据库名、表名、clientId、MQ组／Topic、域名`zj-market.test`、证书或旧历史报告。那些标识参与运行与验收，不做无收益的全链路重命名。

## 4. 页面视觉方案

### 4.1 设计基础

采用清晰的商品优先布局：浅灰背景、白色内容卡片、深色文字、单一蓝色主操作。以下为可执行的首版视觉规格，不改变业务语义：

| 项目 | 建议规格 |
| --- | --- |
| 背景／卡片 | `#F6F7F9`／`#FFFFFF` |
| 正文／次要文字 | `#1F2937`／`#667085`；浅色文字也需检查对比度 |
| 主操作／金额 | 主操作`#2563EB`；价格使用深色或独立强调色，不能只靠颜色区分状态 |
| 成功／提示／错误 | 绿色／琥珀色／红色，均配中文文案与图标 |
| 字体 | 系统中文字体，正文14～16px，商品／页面标题20～28px，金额26～32px |
| 间距／圆角 | 4、8、12、16、24、32px间距；卡片12px，输入／按钮8px |
| 内容宽度 | 桌面约1200px上限；手机左右16px；列表随宽度调整列数 |
| 操作尺寸 | 主要触控区域不小于44×44px；清晰focus-visible |

价格、优惠、状态、主要按钮形成稳定层级。不再对所有button全局设置width:100%，改为Button尺寸／用途变体，避免导航、列表刷新、取消等操作占满屏幕。全宽只用于手机购买确认或收银台主操作。

CSS按tokens、基础控件、布局、业务组件拆分，避免现有账号页main布局影响商城其他页面；不要继续在单行全局CSS末尾无限叠加覆盖。

## 5. 操作流程优化

### 5.1 单独开团与参团

当前“核对开团报价→确认购买→查看订单→进入收银台”改成连续引导，但保留后端确认和创建订单两步：

1. 用户点击“单独开团”或“去参团”，检查本人未结束购买及本地结果未知意图，存在则引导继续原单。
2. 前端调用既有报价确认，展示确认面板：商品、数量1、当前实付、成团人数、开团／指定团队、付款期限说明。用户最终点击“确认下单并去支付”。
3. 只提交一次既有下单请求，保存原purchaseIntentId。202受理后展示“订单正在确认”，查询原单，不能重建意图。
4. A占位确认且后端允许支付后进入原收银台；占位未明、失败、超时、满团或价格变化时展示真实状态，不自动换团或开新团。

选团后继续复用既有`/teams/{teamId}`与JOIN。可在团队页自动准备当前报价确认，省去“再核对”机械按钮，但最终下单仍由用户明确确认。选定teamId、活动、商品和价格变化都必须失效旧确认；涨价或换活动不能自动接受。

正常加载只读状态允许自动查询；“用户明确进入购买确认”可调用确认接口；刷新、返回和进入详情本身不得自动POST建单、付款或取消。建议自动跳转只发生在本次操作所属用户／原订单仍一致时；用户已主动离开则保留提示，不强制拉回页面。

### 5.2 模拟收银台

保留醒目但简短的“演示支付，不产生真实扣款”，重点显示商品、金额、付款倒计时和两种选择：

- 主按钮“模拟支付成功”。
- 次按钮“模拟本次支付失败”，明确订单仍可在期限内重试或取消。

隐藏“创建支付单／创建尝试”技术步骤，由前端编排原接口，不改成前端直接设置商城支付成功：

1. 用户明确选择结果后，检查原pending操作、支付根和当前attempt。
2. 无可用尝试且后端允许时，用稳定operationId创建尝试；只在查明创建结果并取得合法OPEN attempt后提交所选结果。
3. 创建或结果提交未知时先查原操作；保留本次用户选择、userId、orderId与阶段，不能生成新键跳过未知状态。
4. 刷新后恢复原操作并展示“正在确认支付”；自动查询可继续，但新的资金写入不因页面刷新而发起，必要时让用户明确继续原操作。
5. 原尝试失败后只有明确的再次付款动作才能创建下一次尝试；历史已成功则只展示结果，不再提交。

这项优化是有恢复状态的两段编排，不能简单写成`createAttempt().then(chooseResult)`后忽略异步受理、身份变化与断网。使用跨标签锁保留既有互斥，模拟成功／失败按钮在原操作未知时都禁用。金额、支付时间、资格仍由服务端和独立模拟渠道决定。

### 5.3 付款后与分享

付款结果页提供明确进度：“付款结果确认中→已付款，正在确认参团→待成团→成团成功”。显示主要入口“查看拼团／邀请好友／查看订单”。只有确有渠道成功事实才显示付款成功；只有可信成团及本地收尾满足条件才显示待履约。

分享使用当前团队既有链接，提供“复制邀请链接”及复制结果提示；浏览器剪贴板不可用时显示可手动复制文本。页面展示“需要2人付款，当前已付1人，仍可加入1位”，不把待付人数与剩余名额混为一谈，不显示虚假头像或伪造“很多人正在拼”。

### 5.4 我的订单与退款

列表卡片显示商品图／名称、实付、购买方式、中文状态与一个主要行动。详情使用状态横幅＋进度说明＋商品金额＋操作区＋折叠订单信息。

| 可信状态 | 用户主文案 | 主要操作 |
| --- | --- | --- |
| PROCESSING | 正在确认订单，请稍候 | 查看进度；不能重复买 |
| WAITING_PAYMENT | 待付款 | 后端允许时去支付；未付可取消 |
| PAYMENT_PROCESSING／资金UNKNOWN | 正在确认付款结果 | 查看结果，禁止再次发起新付款 |
| PAID_WAITING_A | 已付款，正在确认参团 | 查看进度；不称为未付款 |
| PAID_WAITING_TEAM | 拼团中 | 查看团队／邀请好友 |
| WAITING_REFUND | 拼团未成功，退款处理中 | 查看退款 |
| GROUP_COMPLETED | 成团成功，待履约 | 查看订单；不提供未实现的发货／收货按钮 |
| CLOSING | 正在关闭订单 | 查询原关闭结果，不直接显示已取消 |
| CLOSED | 已关闭；原因按可信事实展示 | 返回商城 |

退款摘要优先说明用户资金状态：退款成功／处理中／需核对。只有fundsStatus确认成功才能写“已退款”；资金成功但库存或A同步收尾尚未完成时，可以写“退款已成功，订单正在收尾”，不能反转成退款失败，也不能虚称全部完成。

“取消订单”改成轻量确认对话框，提供默认原因／常用选项，补充原因选填；请求仍携带后端要求的reason和原operationId。只依据服务端可取消能力显示，支付后不出现主动退团退款。

全局订单状态筛选若需要跨页准确结果，必须补B后端受控status查询／计数再做标签；不能只过滤当前20条却宣称“全部待付款”。首轮先做好已有全量分页列表，筛选为可拆分P2任务。

## 6. 错误反馈、维护状态与启动体验

### 6.1 前端响应处理

在`services/auth.ts`统一处理状态码、Content-Type和正文解析：

- JSON错误转为中文业务提示；缺字段、空正文、HTML、502／503／504均有安全兜底，不展示原HTML和堆栈，不用innerHTML注入响应。
- 200但非JSON／结构非法同样是响应异常，不能当成功；对于写操作保留原意图和恢复入口。
- 读请求可以有限重查；写请求不因自动刷新登录、网络异常或解析错误而换键重放。价格变化、401、409和429各自处理，保留Retry-After。
- 普通提示简短并有明确动作；请求编号放“支持信息”折叠区／复制按钮。不要让用户自己保管长业务编号才能继续。
- 表单校验靠近输入；请求异常在当前操作区域显示。成功提示不能完全依赖短暂toast，页面状态也须反映结果。

### 6.2 网关与就绪检查

P0需同时解决运行层问题：

1. Nginx自身产生的维护503／代理失败返回统一JSON与正确HTTP状态，包含安全错误码及请求编号。B返回的JSON业务错误继续透传，不能用笼统error_page覆盖全部上游错误语义。
2. 为实际加载的网关配置提供只读模式标识，例如新增`GET /api/v1/system/status`返回NORMAL／MAINTENANCE。该路径为拟新增设计，实施时冻结响应；公开仅最小服务可用性，不暴露配置、密钥或内部拓扑。
3. 模式值由Nginx当前加载的开放／维护配置决定，不仅看release.json或挂载文件名；前端显示站点维护提示并禁用新增购买，原恢复功能按实际规则继续。

## 10. 必过验收清单

| 编号 | 场景 | 验收标准 |
| --- | --- | --- |
| UX-T01 | 品牌与导航 | 当前页面统一正经商城，品牌回首页，title与页面对应；技术身份和域名不变 |
| UX-T02 | HTML／空／坏JSON | 中文提示与可恢复动作，无原始堆栈，写操作不误判成功／重建意图 |
| UX-T03 | 维护与重复start | 网关维护被识别；重复start拒绝不使正常商城停写；切换失败仍可保护入口 |
| UX-T04 | 登录／刷新／深链接 | 登录回原路径，刷新不POST；退出／换人不显示原用户订单或支付选择 |
| UX-T05 | 单独开团与JOIN | 明确报价确认，常态步骤缩短；JOIN原teamId固定，不自动换团 |
| UX-T06 | 价格／活动／库存变化 | 新报价需确认，满团／过期／缺货正确拒绝，原单仍能恢复 |
| UX-T07 | 创建订单响应丢失 | 保留原purchaseIntentId，查询／重试原单，无重复预留 |
| UX-T08 | 支付编排两段分别丢响应 | 原operationId／attempt保持；未知不新建资金操作，刷新不自动选择结果 |
| UX-T09 | 多标签与按钮连点 | 同SKU守卫、Web Locks及原操作恢复有效，按钮视觉禁用不是唯一防线 |
| UX-T10 | 成团与失败退款 | 当前资金／团队事实驱动文案；全额退款后唯一释放，成团唯一确认 |

| UX-T15 | 移动与辅助访问 | 目标视口无溢出、触控区≥44px、键盘能完成流程，焦点可见、不被底栏遮挡 |
| UX-T16 | 当前主站与候选 | 两套地址／账号／数据明确；新镜像实际启用，旧报告不冒充新版本验收 |
