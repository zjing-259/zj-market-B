# 项目B开发路线图与阶段划分

日期：2026-10-03。状态：总体规划已建立，各开发阶段待开展；本文不代表阶段实现或验收完成。

本次只确定业务边界、DDD分层方向、开发顺序、阶段目标及验收门槛。具体聚合设计、表结构、框架版本、支付渠道、前端技术和接口实现，在对应阶段开始前再敲定，不在本轮修改工程代码或依赖。

## 1. 目标与当前基线

- 对外提供一个商城前端：用户在B登录、浏览商品、参与拼团、支付、查看订单。B调用A营销能力，用户不需要跳到另一套登录系统。
- A负责活动、优惠资格、拼团占位、参团记录、成团和失败事实；B负责用户、商品、库存、商城订单、资金支付/退款和履约。B不重复实现A的优惠、资格或成团判定。
- B采用DDD，以单个可独立部署的商城服务起步，内部按业务模块组织；不因模块划分就进一步拆出库存、订单、支付微服务。
- 当前B已有Spring Boot基础工程及[业务词汇表](../CONTEXT.md)，尚无完整商城业务。当前POM为Java17、Spring Boot4.1.1，这是已有配置，不等于中间件兼容已经在实际B验证。
- A已达到B接入开发的阶段性条件。已有独立客户端、本机RPC/MQ与业务测试不替代真实B验收。以[A/B接口契约](../../group-buy-market/docs/ab-api-contract.md)为接入基线，参考[A侧交付报告](../../group-buy-market/docs/phase5-ab-v2.md)。契约文件保持单一来源，不在B复制另一份可能失步的正文；阶段记录注明实际使用的契约版本和产物版本。
- 首版拼团购买沿用单SKU、数量1、CNY、最低实付0.01元、不叠加B额外优惠；未支付可取消，已支付不主动退团，团队失败全额退款，到期须核对后才能最终失败。
- 普通非拼团购买、购物车合并下单、多SKU、多币种、部分退款、复杂优惠和真实物流平台接入，均为后续范围选择，不自动纳入首版承诺。首页、商品和订单基础能力仍需建设。

## 2. B的DDD组织方向

### 业务模块与责任

| 模块 | B拥有的职责 | 与A的边界 |
|---|---|---|
| 用户与访问 | 登录身份、个人资料、订单访问权限 | A接收可信B传递的用户标识；营销标签与资格由A判断 |
| 商品 | 商品资料、基础售价、在售状态、商品版本 | B向A同步营销所需商品副本，不同步可扣减库存 |
| 库存 | 可售数量、订单库存预留、释放、转已售 | A拼团名额不能代替库存预留 |
| 商城订单 | 购买快照、外部单号、用户订单进度、取消协调 | 关联A参团记录与团队，不复制A状态机作为决策权威 |
| 支付与退款 | 可信资金结果、支付流水、关支付单、退款及核验 | 向A发送事实，A接收成功不是资金支付成功 |
| 履约 | 成团且付款确认后的待履约、发货/完成等最小流程 | A只发成团事实，不负责库存出库或配送 |

上述是初始业务模块边界，不预先强制每个模块对应独立数据库、Maven工程或微服务。聚合根和一致性边界在阶段设计时确定，避免一个跨商品、订单、支付的巨型聚合。

### 分层约束

- **接入层**：面向前端的HTTP接口、MQ消费入口及任务触发；负责协议转换和入口校验，不放核心交易规则。
- **应用层**：组织“创建商城订单”“确认支付”“处理成团”“核对到期”等用例，协调本地事务、领域操作和对A调用。远程调用不冒充跨库本地事务。
- **领域层**：实体、值对象、领域服务和规则，例如库存不能超卖、同订单不能重复释放、已退款不能履约。领域不依赖Dubbo、RocketMQ或具体数据库实现。
- **基础设施层**：持久化、A的Dubbo适配器、RocketMQ、资金渠道适配器、Outbox/Inbox存储等，实现上层定义的端口。
- **启动与配置**：依赖装配、环境配置和启动入口。是否拆Maven模块、包名及模块依赖在阶段1决定。

A共享契约DTO只在集成边界使用，通过适配转换为B用例输入和领域对象；不把A数据库实体当作B订单模型。Outbox/Inbox是可靠集成机制，不单独充当业务领域。

## 3. 总体开发顺序

阶段1基础与互通 → 阶段2用户商品与浏览 → 阶段3订单库存与占位 → 阶段4支付与成团 → 阶段5失败核对与退款 → 阶段6完整联调及部署验收。

前端跟随阶段2～5逐步形成可用页面，不先做完所有页面再接后端。每个阶段都进行对应A/B真实调用验证，最后一阶段做全流程与故障联合验收，避免最后才第一次连接。

| 编号 | 阶段 | 前置依赖 | 阶段成果 | 验收门槛 | 状态 |
|---|---|---|---|---|---|
| B-01 | DDD骨架与技术互通 | 当前A契约及可用开发环境 | B分层骨架、独立数据边界、真实RPC/MQ最小链路 | 实际B进程能调用A并收发授权消息；版本、认证和错误处理可复现 | 待开展 |
| B-02 | 用户、商品与商城浏览 | B-01 | 登录、商品资料/版本/在售状态、商品同步、商城首页及拼团展示 | A按B版本试算；乱序不覆盖新商品；身份与商品权限有效 | 待开展 |
| B-03 | 商城订单、库存与拼团占位 | B-02 | 稳定外部单号、库存预留、A占位/查单、未支付关闭、待支付页面 | 并发不超卖；重复不多占；超时可恢复；取消后库存与名额收敛 | 待开展 |
| B-04 | 支付事实与成功成团 | B-03 | 支付接入、事实发送、结果接收、成团后待履约、状态展示 | 支付/消息重复不重复计数或履约；成团早于支付回执也可恢复 | 待开展 |
| B-05 | 到期核对、失败退款与任务恢复 | B-04 | 资金核对、团队失败、全额退款、库存释放、异常订单处理 | 未知付款不伪造未支付；失败可退款；重复/乱序/重启不重复释放或退款 | 待开展 |
| B-06 | 完整商城联调与部署验收 | B-01～05完成 | 真实B全流程、故障矩阵、部署与回滚资料 | 库存/资金/订单/团队最终一致，跨主机与必要安全验证完成 | 待开展 |

## 4. 阶段范围与后续设计入口

### B-01：DDD骨架与技术互通

- 明确模块、分层依赖、配置边界和B独立数据库；建立最小契约消费端和MQ入口，不开发完整交易。
- 在实际B运行时验证A契约包、Dubbo/Triple、RocketMQ、认证、权限和序列化。已有JDK21运行release17客户端的结论不能替代目标JDK17验证；如调整运行时，另行记录选型依据。
- 确立日志关联和隔离测试原则，为Outbox/Inbox后续落地留出基础设施边界。
- 后续敲定：工程拆分、依赖版本、持久化工具、配置方式、目标JDK及环境启动方式。

### B-02：用户、商品与商城浏览

- 建立登录与必要的角色/资源权限、商品最小管理与查询、基础价格和商品版本；前端完成登录、首页、商品列表/详情和拼团价格展示。
- 商品更新与待发布事实本地原子保存，首次落地Outbox；接收A商品处理结果时建立Inbox和幂等模式，后续阶段复用。
- 商品同步未完成或A版本不符时明确展示暂不可购买/待恢复状态，不直接沿用未核验价格下单。
- 后续敲定：登录方式、前端框架、商品维护入口、最小字段、展示布局与同步恢复策略。先按用户可理解的页面实现，不向用户暴露MQ等内部机制。

### B-03：订单、库存、占位与未支付关闭

- B生成稳定外部单号，在本地事务形成商城订单、库存预留和待协调任务，再向A占位；保存A成交快照后开放付款入口。
- 超时保持待确认，通过查单和原键重试恢复；明确拒绝或成功关闭后才按规则释放库存。关闭先于迟到占位时，利用A关闭标记防止重新建单。
- 用户只能查看/操作本人订单；订单页能区分处理中、待支付和已关闭，不将服务超时直接显示为购买失败。
- 后续敲定：订单/库存聚合、状态与事务边界、预留记录、并发控制、关闭任务。此阶段尚无真实支付时只验从未开放支付的取消；已创建资金支付单的关闭与支付竞争在B-04/05补验。

### B-04：支付事实、成团与最小履约

- B保存可信付款结果和待发布事件同事务，可靠发送PAYMENT_SUCCEEDED；记录“A接受待确认”和结果事件，不能用Broker发送成功代替A已处理。
- 消费A成团事件，只有本地资金核对通过才把预留转为已售并进入待履约；覆盖消息早到、重复、结果丢失和查询恢复。
- 前端完成支付入口/结果、待成团与成功订单展示，履约先按最小需求闭环，不预先承诺对接物流平台。
- 后续敲定：支付渠道或沙箱、回调验真、查询/关单能力、履约最小范围。若先用可控支付模拟器，只视为功能联调，不能宣称真实资金链路验收通过。

### B-05：失败核对、退款与恢复

- 响应A到期核对事件，停止新支付、查询资金事实，完整核对名单；未知资金状态保持处理中并告警，不凭本地超时强行宣布失败。
- 接收失败结果，已付款订单创建幂等全额退款；分别管理库存释放与退款进度。支付后不支持主动退团，符合既定契约。
- 处理付款成功但A拒绝、支付晚于截止、退款消息乱序、重复失败通知和重启；后台任务能够继续执行而不是依赖用户刷新页面。
- 后续敲定：支付异常处置、退款任务状态、等待依赖、对账周期、最小人工恢复工具。完整运营操作台可以后续建设，但最小可审计恢复方式不可缺失。

### B-06：完整联调、故障和部署

- 以实际B而非测试夹具跑完整成功链路与失败退款链路；检查金额快照、支付唯一性、库存守恒、名额、订单和履约状态。
- 演练消息乱序/重复、提交后响应或ACK丢失、服务重启、多实例竞争、MQ/Redis故障、业务消费组重试与死信恢复。
- 验证目标运行时、跨主机地址、Broker TLS、正式证书配置、权限及密钥轮换，重建匹配源码的镜像，明确旧HTTP入口及通知任务的切换边界。
- 后续敲定：部署环境规模、压测目标、日志/监控组件、备份及回滚方式。Docker优先考虑，不默认引入K8s或Service Mesh。

## 5. 文档、状态与验收管理

- B项目代码、前端资产及开发文档均存于 `zj-market`；前后端具体子目录在阶段1/2确定。本路线图作为总体入口，业务词汇沿用根目录CONTEXT.md。
- 阶段详细设计和验收记录后续放在B的 `docs/` 中，建议每阶段一份文档，包含目标、范围、实现决策、接口依赖、验收命令、实际结果、剩余问题和复杂度。暂不创建空壳阶段文档或预先写死表结构。
- 阶段状态：待开展 → 设计确认 → 开发中 → 待验收 → 已验收。仅文档写完或编译成功不代表业务阶段完成。
- 每阶段开始时再确定实现选项；影响业务规则、数据归属或交互体验的分歧交由用户选择。对A契约的新需求先记录差异，不能在B绕过身份/价格/关闭规则；经确认修改A契约并补回归。
- 阶段验收优先覆盖新增规则、并发及故障场景；不机械重复全部历史测试，也不把模拟结果当作真实渠道/实际部署证据。
- 进入下一阶段前记录未完成项：区分阻塞项与可延后项。直到阶段5完成前，成功链路演示都不等于完整商城已具备上线条件。

## 6. 本次更新的复杂度评估与拆分

**本路线图所规划的B开发整体复杂度：高。** 原因是商品版本、库存预留、商城订单、真实支付、A参团结果及退款横跨两个服务，存在独立事务、异步消息和结果未知；技术难点集中在正确恢复业务事实，而不只是接入Dubbo/RocketMQ。本文编辑本身不代表这些任务已完成。

因此按六个小阶段推进，并将高复杂度阶段进一步分成可独立验收的小步：

| 阶段 | 复杂度 | 小步与验收点 |
|---|---|---|
| B-01 | 中 | 分层骨架与配置 → 实际B调用一个A查询 → MQ授权收发；每步能够独立启动验证 |
| B-02 | 中 | 登录/权限 → 商品及版本 → 商品同步/试算 → 商城浏览；版本错配与越权有明确结果 |
| B-03 | 高 | 本地订单/库存原子预留 → A占位及结果恢复 → 未支付关闭；分别验并发库存、原键重试、取消与迟到请求 |
| B-04 | 高 | 可信支付事实 → MQ支付及A结果 → 成团及待履约；分别验资金判定、幂等计数、无重复履约 |
| B-05 | 高 | 到期名单核对 → 失败退款/库存释放 → 重启与异常恢复；分别验未知资金保留、幂等退款、恢复收敛 |
| B-06 | 高 | 实际B全流程 → 故障矩阵 → 跨主机安全部署/回滚；各自保存真实验收证据，不以一项通过替代其余 |

阶段依赖以第3节为准；具体实现和工作量估算在各阶段设计时确定。本次仅新增路线图，未修改A、B业务代码、数据库或依赖。
